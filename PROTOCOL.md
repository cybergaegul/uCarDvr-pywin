# XUFS Camera Protocol Documentation v1

> Live verification completed with an early unit purchased in 2020 (confirmed status responses + 1280x720 MJPEG frame reception).
> Subsequent models may have firmware variations, so compatibility cannot be guaranteed.
> Everything here is verified by observing the physical hardware and testing interoperability.

## 1. Architecture — A "Mass Storage Mailbox", Not UVC

The camera (Generalplus SoC, device name "CAR_DVR USB-MSDC DISK A", VID `0x1B3F` / PID `0x8301`) enumerates exclusively as a USB Mass Storage device. This is why Windows does not recognize it as a standard camera.

Host-to-camera communication mechanism:
1. When plugged into USB, it mounts as a storage drive. A file named **`elen1`** (exactly 307,200 = 0x4B000 bytes) exists in the root directory.
2. The host reads this file using Direct I/O (bypassing the OS cache).
3. **Command Transmission** = Executing sequential reads at the `elen1` offset `0x3E800` (500 sectors), where the **commands are encoded within the read sizes**. As each read is issued as an individual SCSI READ(10) command, the firmware interprets the (LBA, Transfer Length) pattern.
4. **Response/Video Reception** = The firmware writes data to the `elen1` area → The host polls sector 0 of `elen1`.

`elen1` acts as the host↔camera mailbox. `zlog` (10 bytes of `4D CC` × 5) is a marker file generated by the camera.

## 2. Disk Structure (Verified on Physical Device)

| Item | Value |
|---|---|
| MBR Partition Start | **Absolute LBA 223 (0xDF)** — Verified via boot sector hidden sectors (0x1C). |
| BPB | 512B/sector, 8 sectors/cluster (4KB), 32 reserved, 2 FATs × 2044 sectors, root cluster 2. |
| Data Region Start | **Volume LBA 4120** |
| Root Directory | ELEN1 (Cluster 3), UCARDVR.APK (78), ZLOG (198). |
| elen1 Data Start | **Volume LBA 4128** (75 contiguous clusters) = Absolute LBA 4351. |
| **Mailbox (0x3E800)** | **Volume LBA 4628 = Absolute LBA 4851** |

⚠️ **In a FAT volume, the LCN returned by `FSCTL_GET_RETRIEVAL_POINTERS` is a relative value (FAT cluster − 2) based on the data region start.** Volume Offset = Data Region Start + (LCN × Sectors per Cluster). Mistaking the LCN for an absolute volume offset will cause a 4120-sector (2MB) misalignment — this was the biggest pitfall of this project.

## 3. Command Transmission Format

Payload format: `cmd` (u16 LE) + `arg1` (u16 LE) + `payload` (≤0x20 bytes).
Reads are performed sequentially at the mailbox offset (0x3E800):

| Seq | Read Size | Meaning |
|---|---|---|
| 1 | `0x2200` (17 blocks) | Packet Start |
| 2 | 2 times per byte | Nibble Encoding |
| 3 | `0x2400` (18 blocks) | Packet End |

Nibble Encoding: For byte `b` → issue `read((b & 0xF or 16) << 9)`, then `read((b >> 4 or 16) << 9)`. (Nibble 0 is encoded as 16 blocks to avoid 0-length reads). The offset is reset between each read. The read data is discarded.

## 4. Response Packets

Read **Sector 0** of `elen1` → If the first 2 bytes are `55 AA`, it is a control response:

```text
0x00: 55 AA          Sync
0x02: u16 cmd        (Response type)
0x04: u16 arg        (Observed example: cmd=9 → arg=0x420)
0x06: u16 len        (Payload length)
0x08: u16            (Unused)
0x0A: payload[len]   (If len > 0x1F7, it continues to the next sector; additional read of (len+9)&~0x512 is required)
```

Response `cmd`: `5` = File list, `0x21` (decimal 33) = **Audio PCM (32000Hz Mono 16-bit LE — Empirically measured)**, `29` = Device info string, `48` = Playback seek ACK (arg=requested seconds), `57` = Playback file length (arg), `240` = Firmware/Model string, `0xF0`/`0x1D` = Strings.

### File List (cmd 5) — 6-byte entry, 0xFFFF termination

**Confirmed (Device observation & Interoperability tests)**:
- **LOCK flag = Bit 0 of the packed datetime u32** (bit0==0 → "MOVI%04d", bit0==1 → "LOCK%04d").
- Category is a query argument: 0x0000 = Video (returns both MOVI+LOCK), 0x8000 = Photo (PICT), 0x4000 = Rear camera.
- The `|0x8000` in Delete (cmd 20) is the **Photo (PICT) flag**, NOT the LOCK flag.
- The `arg` for Lock (cmd 21) / Unlock (cmd 22) is the **plain file ID** (no flags).
- The second value of a locked file incorporates bit 0 for encoding, so a ±1 second discrepancy is possible.

```text
u16 file_index   (MOVI/LOCK/PICT number)
u32 packed:  sec=v&0x3F, min=(v>>6)&0x3F, hour=(v>>12)&0x1F,
             day=(v>>17)&0x1F, mon=(v>>22)&0xF, year=2000+(v>>26)
```

## 5. Video Frames — Live Verification Complete

⚠️ **CRITICAL (Empirical observation): The camera responds to frame requests (cmd 58) ONLY when actively recording (cmd 1 active).** There is no dedicated preview-only mode — whenever it appears to be previewing, the camera is actually auto-recording in the background. If recording is stopped via cmd 2, the frame stream permanently halts and cannot be recovered even by restarting the program (requires camera power cycle). Live view = simultaneous recording is a mandatory design constraint. This also explains the fps drop when an SD card is inserted — SD write operations and streaming contend within the firmware.

If Sector 0 does **NOT** start with `55 AA`, it is a frame header:

```text
0x00: u32 total_len    (Observed example: 113,682 = 0x1BC12; Valid range ≤ 0x4AFFE)
0x04: u16 type         (Observed: 0x0002)
0x08: 8 bytes          (Presumed timestamp)
0x10: JPEG Data Start  ← Confirmed: FF D8 FF E0 (SOI+APP0), "GPEncoder" signature, SOF0 = 1280x720, 3 components 4:2:0
```

**Full JPEG = `elen1[0x10 : 0x10+total_len]`** (~110KB/frame HD MJPEG).
Read process: Read Sector 0 (0x200B), then sequentially read `ceil((0x10+len)/512)` sectors starting from offset 0.

⚠️ Confirmed anomaly: The encoder **injects ~2.3KB of extraneous data between the end of the scan data and the EOI (FFD9)**. libjpeg/OpenCV throws an "extraneous bytes before marker 0xd9" warning, but decoding proceeds normally. The viewer handles this by truncating at the first EOI.

### Identity of the Extraneous Data (Presumed: Encoder Fixed Buffer Padding)

Background — The camera device itself lacks standalone sensors (Hardware verified):
- **No G-Sensor/GPS**: Collision detection, parking mode, and GPS are features/sensors of the host (Android Head Unit).
- **ADAS is also host-side**: FCWS+ADAS are app-level features; image recognition is processed in software on the Android unit.
→ The camera lacks any telemetry sources to embed.

Therefore, the most plausible explanation is **fixed-size frame buffer padding by the encoder**:
- If the compression result (scan data) is shorter than the fixed buffer, it seems to write the **EOI (FFD9) at the very end of the buffer** instead of filling the remaining space.
- Observational evidence: The extraneous data size fluctuates between 2,251 and 2,318 bytes per frame — perfectly inversely correlating with the scan length variations based on scene complexity.
- The padded area may contain uninitialized memory or remnants of previous frames (unlikely to contain useful data).
- Verification method (if interested): Check if the sum of (scan length + extraneous data size) remains constant across static vs. complex scenes. If constant, a fixed buffer is confirmed.

Note: The 1280x720P resolution advertised on product pages matches the empirical SOF data (1280x720).

## 7. Windows Implementation Notes (xufs_lib.py)

- **Nibble signaling directly issues SCSI READ(10)** (`IOCTL_SCSI_PASS_THROUGH_DIRECT`):
  - Volume handles are denied (Error 5) → Must open `\\.\PhysicalDriveN` with **GENERIC_READ|GENERIC_WRITE** (IOCTL requires R|W mask; actual issue is READ only).
  - Buffers must be 4096-aligned; single SPTD capped at 32KB (Error 6 at 64KB), bulk transfers use 32KB chunks.
  - `ctypes`: `sptd.Cdb[:len(cdb)] = cdb`.
- Triple Offset Compensation: ① LCN relativity (BPB data region base) ② MBR partition +223 ③ Intra-file offset.
- `GET_PARTITION_INFO_EX` returns Error 50 (Unreliable) on this device — substituted with hidden sectors.
- ScsiVolumeReader automatically determines the disk/offset via boot sector content matching (Candidates → 8MB scan → Next disk).
- OpenCV 5.0: `imdecode` strictly requires numpy arrays (`np.frombuffer`).

## 9. SD Card File Access (Live Verification Complete, 2026-11-22)

### Core Facts
- **The SD card is NOT exposed as a drive to Windows.** The camera only mounts the internal 1.1GB mailbox partition; SD recordings are accessible solely via the protocol.
- **SD insertion + Power ON = Auto loop recording starts** (Status response arg bit 0x02). You must stop recording via cmd 2 before downloading files.
- **RTC resets on power cycle** (Default: 2018-04-15 00:00:00) — You must synchronize the time via cmd 19 at session start for new files to bear accurate timestamps.

### File Playback/Extraction Protocol (★Live Verified)

```text
cmd 2           Stop recording
cmd 5 (arg1=0)  File list → 6B entry array (Index = file number, newest first)
cmd 6 (arg1=id) Start playback → Stream begins immediately (★arg1=0x0000 empirically successful)
    Frame Channel: Arrives at Sector 0 frame header (~105KB JPEG, ~25fps, type field observed: 0x0000/0x0421, post-seek mixed with 'TB'/0x0002)
    Audio Channel: Response cmd 0x21 (decimal 33) 9216B/chunk ≈ 144ms (32kHz mono s16)

⚠️ During live view, 0x21 audio is NOT sent (Empirical observation + host app lacks live audio sync). Audio is recorded to files and streams ONLY during playback. ★Empirical: Sound confirmed in playback files (Mic capture normal).
The viewer/player volume controls the audio during file playback.
    Speed: ~2.5MB/s (Dependent on read speed; a 3-minute file takes several minutes).
cmd 48 (sec)    Seek — Response arg=requested value ACK
cmd 57          Query playback length — arg = file_arg(id, kind) mandatory (arg=0 yields no response), Response arg = MediaLength(sec)
cmd 8           Stop playback ★ (cmd 2 does not stop playback)
cmd 7           Pause playback
```

- **There is no dedicated bulk download command** — It relies on capturing and reassembling the playback stream.
- Stream frames are pristine JPEGs (720p 4:2:0), so truncating at the first EOI and repacking into an MJPEG AVI produces a playable file (`xufs_lib.write_mjpeg_avi`).
- **Audio is MUXED into the same AVI** (`xufs_lib.write_avi_with_audio`, 32kHz mono s16le, PCM non-interleaved — pure Python with no dependencies). Downloads output as single .avi files.
- **FPS Reverse Calculation**: Audio chunks act as a real-time clock — `fps = Frames / (AudioBytes / 64000)`. Defaults to 25fps if no audio.
- Live viewer is unusable during playback (single mailbox channel).
- **Resumes recording on exit**: The app sends cmd 1 after exit confirmation — leaving the camera in its continuous recording state.
- Rapid transition warning: A cmd 6 immediately following a stop (cmd 8) might be ignored. The app handles this by flushing the mailbox, checking a 0.25s quiet period, and auto-recovering on a 6s timeout.
- Tools: `xufs_player.py` (GUI — sortable headers / playback with audio, volume, seek, loop, auto-play next / previous & next / delete & protect / selective & bulk download).
